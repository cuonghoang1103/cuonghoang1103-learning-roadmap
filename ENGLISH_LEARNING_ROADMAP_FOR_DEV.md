## C.2. TECHNICAL INTERVIEW — CÂU VÀ CỤM TỪ

### C.2.1. KHI BẮT ĐẦU (Opening)

| Mẫu câu | Dùng khi |
|---|---|

| "Let me start by clarifying the requirements..." | Hỏi rõ yêu cầu trước |
| "Before I dive in, can I ask a clarifying question?" | Cần hỏi thêm |

### C.2.2. KHI SUY NGHĨ (Thinking)

| Mẫu câu | Dùng khi |
|---|---|
| "So basically..." | Bắt đầu giải thích đơn giản |
| "The idea here is that..." | Giải thích concept |

| "So if I understand correctly..." | Paraphrase câu hỏi |
| "Hmm, that's a good point. I think..." | Phản hồi có suy nghĩ |
| "From my understanding..." | Trình bày hiểu biết |
| "I'm not 100% sure about this, but..." | Nói ra điều không chắc chắn |

### C.2.3. KHI TRÌNH BÀY THUẬT TOÁN (Algorithm)

**Bước 1 — Outline:**
```
My approach would be to use [Data Structure]. Here's my plan:

First, I'll [do X].
Then, I'll [do Y].
Finally, I'll [do Z].

Does that sound like a reasonable approach?
```

**Bước 2 — Chi tiết:**
```
I'll create a [HashMap] to store [key-value pairs].
For each element, I'll check if [condition].
If yes, I'll [action]. Otherwise, I'll [action].

The key insight here is [important detail].
```

**Bước 3 — Đánh giá:**
```
So the time complexity would be O(n) because [reason].
The space complexity would be O(k) where k is [what k represents].

Let me write the code for this.
```

**Bước 4 — Nếu bị stuck:**
```
I'm not 100% sure about the optimal solution, but here's
my initial thought... [idea]. Actually, let me reconsider...
I think the better approach would be...

Can I use a [data structure] here?
```

**Bước 5 — Sau khi code xong:**
```
I've written the code. Let me trace through it with an example.
If the input is [example], the first step [X] happens,
then [Y], and the output is [result]. It looks correct.
Are there any edge cases you'd like me to consider?
```

### C.2.4. KHI GIẢI THÍCH CODE

```
This function [method name] takes [parameters] as input
and returns [what it returns].

It works in three steps. First, [step 1]. Then, [step 2].
Finally, [step 3].

The key thing to note here is [important detail].
For example, if the input is [example], the output
would be [output].

One potential issue is [edge case], which I would handle
```

## C.3. CODE REVIEW — CÂU VÀ CỤM TỪ

### C.3.1. GIVE FEEDBACK (ĐƯA PHẢN HỒI)

**Nhẹ nhàng — Suggestion:**
```
Hey [name], great work on this PR! I have a few small
suggestions:

- Could we extract this into a helper method? It might
  make the code more readable.
- Have you considered using [alternative approach]?
  It might be slightly more efficient.
- I think renaming [X] to [Y] would be clearer.

Let me know what you think!
```

**Kỹ thuật hơn:**
```
I think we can simplify this by [specific change].

Right now, [describe current code] runs in O(n^2).
If we use a [HashMap], we can bring it down to O(n).
What do you think?

Also, there's a potential [bug/race condition] here.
If [edge case], this could cause [problem].
We should add [suggested fix].
```

**Nghiêm túc — Bug/Issue:**
```
I spotted something that might cause a problem here.

If [edge case], this could throw a [NullPointerException].
For example, if [specific scenario], [current behavior]
would [result].

We should add a null check before accessing [variable].
Also, have you considered [another risk]?

Let me know if you want to pair on this.
```

**Approval:**
```
LGTM! (Looks Good To Me) — just one tiny nitpick:
can we rename [variable] to something more descriptive?

Otherwise, good to merge! Nice work on this feature.
```

### C.3.2. RECEIVE FEEDBACK (NHẬN PHẢN HỒI)

| Situation | Response |
|---|---|
| Agree with feedback | "That's a valid point. I'll fix it now." |
| Disagree politely | "I see your point, but I think the current approach is better because [reason]. What do you think?" |
| Need clarification | "Could you explain what you mean by [X]? I'm not 100% sure." |
| Accept all | "Thanks for the thorough review! I'll address all of these before merging." |
| Too many comments | "Thanks! I'll tackle these one by one. Can we prioritize the critical ones first?" |

### C.3.3. CÁC CỤM TỪ CODE REVIEW HAY DÙNG

| Situation | Phrase |
|---|---|
| Nhỏ nhưng quan trọng | "Just a small nitpick..." |
| Có thể gây bug | "This might cause a [NPE/bug] in [edge case]..." |
| Nên cải thiện | "Consider using [X] instead..." |
| Tuyệt vời | "Nice approach! I especially like how you..." |
| Không hiểu | "Can you clarify why you chose [X] over [Y]?" |
| Lớn quá, chia nhỏ | "This function is getting a bit large. Could we extract [X] into a separate method?" |
| Thiếu test | "Should we add a test case for [scenario]?" |
| Nên dùng enum | "This looks like a good candidate for an enum..." |
| Hard-coded giá trị | "Can we extract this magic number into a constant?" |
| An toàn null | "Should we add a null check here?" |

# PHẦN D: NGỮ PHÁP THEO GIAI ĐOẠN

## D.1. GIAI ĐOẠN 1 — Foundation Grammar (Tuần 1-8)

### Week 1-2: Present Simple & Present Continuous

**Present Simple** — Thói quen, sự thật, thường xuyên:
```
I write code every day.
Java is a programming language.
He works as a developer.

(+) I / You / We / They write code.
(-) I / You / We / They do not (don't) write code.
(?) Do I / you / we / they write code?

(+) He / She / It writes code.
(-) He / She / It does not (doesn't) write code.
(?) Does he / she / it write code?
```

**Present Continuous** — Đang làm tại thời điểm nói:
```
I am writing a function right now.
She is debugging the code at the moment.
They are reviewing the pull request.

(+) I am (I'm) writing
(-) I am not (I'm not) writing
(?) Am I writing?

(+) He is (He's) writing
(-) He is not (isn't) writing
(?) Is he writing?
```

**Trong ngữ cảnh Tech:**
```
The function takes a parameter and returns a value.
We are currently migrating the database.
He is working on the authentication module.
The server is running on port 8080.
I am implementing the login feature today.
```

**Lỗi thường gặp (Vietnamese speakers):**
```
❌ "I am writing code from 2 hours." (sai — đây là Present Perfect)
✅ "I have been writing code for 2 hours." (đúng)
✅ "I started writing 2 hours ago." (đúng — Past Simple + duration)

❌ "He is knowing the answer." (sai — "know" không dùng continuous)
✅ "He knows the answer." (đúng)

❌ "I need the document. I am reading it now." (sai nếu là thói quen)
✅ "I need the document. I'll read it now." (đúng — future với will)
```

### Week 3-4: Past Simple & Past Continuous

**Past Simple** — Hành động hoàn thành trong quá khứ (thời gian cụ thể):
```
I fixed the bug yesterday.
She deployed the app last week.
We wrote the test cases last night.

(+) I wrote
(-) I did not (didn't) write
(?) Did I write?

Regular verb: work → worked → worked
Irregular verb: write → wrote → written
```

**Past Continuous** — 2 hành động xảy ra song song trong quá khứ:
```
I was debugging when the server crashed.
While she was writing tests, he was reviewing PRs.

(+) I was writing
(-) I was not (wasn't) writing
(?) Was I writing?
```

**Trong ngữ cảnh Tech:**
```
I wrote a function yesterday that handles user input.
She was testing the API when the error appeared.
While we were migrating the database, users reported issues.
He deployed the changes last Friday.
I didn't have access to the production server.
Did you push the code to GitHub?
```

**Lỗi thường gặp:**
```
❌ "I have wrote a function." (sai — không dùng have + wrote)
✅ "I wrote a function." (đúng)

❌ "She have fixed the bug." (sai — sai subject-verb agreement)
✅ "She fixed the bug." (đúng)

❌ "When I have arrived, he left." (sai — dùng Past Simple)
✅ "When I arrived, he had already left." (đúng)
```

### Week 5-6: Present Perfect

**Present Perfect** — Quá khứ liên quan đến hiện tại:
```
I have fixed 3 bugs today.
She has worked on this project for 2 months.
I have never used Docker before.
We have already deployed the app.

(+) I have (I've) fixed
(-) I have not (haven't) fixed
(?) Have I fixed?

Form: have/has + past participle
```

**Trong ngữ cảnh Tech:**
```
I have already implemented the login feature.
We have not decided on the database yet.
Have you tried restarting the server?
She has been working on this for a week now.
I have fixed that bug — it should work now.
How many times have you deployed this month?
```

**Lỗi thường gặp:**
```
❌ "I have implemented it yesterday." (sai — có specific time → Past Simple)
✅ "I implemented it yesterday." (đúng)

❌ "I have seen that error before." (có thể sai ngữ cảnh)
✅ "I saw that error yesterday." (nếu có thời gian cụ thể)

❌ "He has left the company last week." (sai)
✅ "He left the company last week." (đúng)
✅ "He has left the company. (He is no longer here.)" (đúng — không cần time)
```

**Present Perfect vs Past Simple — QUAN TRỌNG:**
```
Present Perfect:          Past Simple:
───────────────           ─────────────
Không nói thời gian       Nói thời gian cụ thể
"for 2 weeks"            "yesterday"
"already, yet, ever"     "last Monday"
"have done, have been"  "did, was, went"
```

### Week 7-8: Future & Conditionals

**Will vs Going to:**
```
Will  = quyết định tại thời điểm nói (spontaneous)
  "I'll deploy the app now." (quyết định ngay lúc này)
  "I'll help you with that bug." (đề nghị ngay lúc này)

Going to = kế hoạch đã có từ trước
  "I'm going to learn React next week." (đã lên kế hoạch)
  "The server is going to crash. I can see the logs." (dự đoán với bằng chứng)
```

**Conditional Type 1 (có thể xảy ra):**
```
If + Present Simple, will + verb

If I fix the bug, the app will work.
If the API is down, we will switch to the backup.
If the user is logged in, we will show the dashboard.
```

**Conditional Type 2 (giả định, không có thật):**
```
If + Past Simple (were), would + verb

If I were a senior developer, I would earn more.
If the server could handle more traffic, we would not
need to scale.
If we had more time, we would write more tests.
```

**Conditional Type 3 (quá khứ, không có thật):**
```
If + Past Perfect, would have + past participle

If I had studied harder, I would have passed the interview.
If we had tested it, we would not have deployed the bug.
```

**Trong ngữ cảnh Tech:**
```
If the query is slow, we should add an index.
If the user is logged in, we will show the dashboard.
If I were to redesign this, I would use microservices.
If we had used a cache, the response would have been faster.
```

## D.2. GIAI ĐOẠN 2 — Building Grammar (Tuần 9-20)

### Week 9-10: Passive Voice

**Passive Voice — Khi người làm không quan trọng hoặc muốn nhấn mạnh kết quả:**
```
Active:     Java runs on the JVM.
Passive:   Java is run on the JVM by the JVM.

Active:     The developer wrote the code.
Passive:   The code was written by the developer.

Active:     They are deploying the app.
Passive:   The app is being deployed.

Active:     We will launch the feature tomorrow.
Passive:   The feature will be launched tomorrow.
```

**Trong ngữ cảnh Tech:**
```
The code is reviewed by the team lead.
Bugs are fixed by the backend team.
The database was migrated last night.
The API is being tested right now.
The credentials should be stored securely.
The bug has been fixed and deployed.
The system will be updated this weekend.
```

### Week 11-12: Relative Clauses

**Relative pronouns:**
```
who / that  → người        → The developer who wrote this code...
which / that → vật         → The function which handles...
whose       → của ai        → The developer whose PR was approved...
where      → nơi           → The server where the data is stored
when       → khi           → The day when we launched...
```

**Defining vs Non-defining:**
```
Defining (không có dấu phẩy — bắt buộc):
  "The function that handles the error is here."
  "Developers who work here earn well."

Non-defining (có dấu phẩy — bổ sung thông tin):
  "My colleague, who works on the frontend, helped me."
  "GitHub, which hosts millions of projects, is popular."
```

### Week 13-14: Modal Verbs

```
can      → có thể         → Can you explain this code?
could    → có thể (lịch sự) → Could I ask a question?
may      → có thể (trang trọng) → May I suggest an alternative?
might    → có thể (không chắc) → This might cause a bug.
must     → bắt buộc        → You must back up the database.
should   → nên             → You should write a test for this.
would    → sẽ (lịch sự)   → Would you like me to explain?
will     → sẽ              → The server will be down tomorrow.

Modal + have + past participle = diễn tả quá khứ / giả định
  should have done → đáng lẽ phải làm (nhưng chưa)
  could have done  → có thể đã làm (nhưng không)
  would have done → đáng lẽ sẽ làm (nhưng không)
```

**Trong ngữ cảnh Tech:**
```
You should write a test before deploying.
The code should have been reviewed.
You should not push directly to main.
This could be optimized further.
The server must be restarted for the changes to take effect.
Could you review my pull request?
Would you mind explaining this approach?

Past regrets:
  "I should have written tests earlier."
  "The bug could have been caught if we had tested more."
```

### Week 15-16: Reported Speech

**Reported Speech — Nói lại câu của người khác:**
```
Direct:     "The bug is fixed," he said.
Reported:   He said that the bug was fixed.

Direct:     "I will deploy the app," she said.
Reported:   She said she would deploy the app.

Direct:     "Can you help me?" he asked.
Reported:   He asked if I could help him.

Direct:     "Don't push to main," the manager said.
Reported:   The manager told us not to push to main.

Lưu ý: Chuyển thì khi reported verb ở quá khứ
  will → would, can → could, is → was, are → were
```

### Week 17-20: Causative & Practice

**Causative have/get something done:**
```
I had my code reviewed by a senior developer.
She got her laptop fixed.
We should get the server checked.
They had the bug fixed quickly.
```

**Q2: "How does the internet work?"**
```
Great question. Let me walk you through it step by step.

First, when you type a URL, your browser sends a DNS
request to find the IP address of that domain.

Then, your browser establishes a TCP connection with the
server using a 3-way handshake: SYN, SYN-ACK, ACK.

Once connected, the browser sends an HTTP request for
the page. The server processes the request and sends
back an HTTP response with the HTML.

Finally, the browser parses the HTML, finds linked CSS
and JavaScript files, and renders the page.

Along the way, routers and switches at various network
points help route the data from your computer to the
server and back.
```

**Q3: "What is the difference between SQL and NoSQL?"**
```
Good question. There are a few key differences.

First, data model. SQL databases use structured tables
with rows and columns, like a spreadsheet. NoSQL databases
store data as documents, key-value pairs, or graphs.

Second, schema. SQL has a fixed schema — you define the
structure before inserting data. NoSQL is schema-less,
which makes it more flexible.

Third, relationships. SQL is great for related data —
you can join tables easily. NoSQL handles relationships
differently — some databases encourage denormalization.

Fourth, scalability. SQL typically scales vertically —
bigger server. NoSQL can scale horizontally — more servers.

Use SQL when you have structured, related data and need
ACID transactions. Use NoSQL when you need flexibility
and can sacrifice strict consistency.
```

**Q4: "Explain REST API."**
```
REST stands for Representational State Transfer.

A REST API is a way for two applications to communicate
over HTTP. It follows a few key principles:

First, client-server architecture — the client and server
are independent. The server doesn't care what the client
looks like.

Second, stateless — each request contains all the
information the server needs. No session is stored on
the server.

Third, cacheable — responses can be cached to improve
performance.

Fourth, it uses standard HTTP methods: GET to read data,
POST to create, PUT/PATCH to update, DELETE to remove.

Resources are identified by URLs, and data is typically
exchanged in JSON format.
```
